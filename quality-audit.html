⚠ Critical Bugs Fix before shipping
Critical
C1 · src/services/order-service.ts:84-94 + src/services/discount-service.ts:189-205
Race condition: stock can oversell and discount limits can be exceeded

Stock oversell (order-service.ts:77-94): The stock check and decrement are two separate operations inside the same transaction but without any locking. SQLite's default isolation allows two concurrent transactions for different carts containing the same product to both read stock = 5, both pass the check, and both deduct, resulting in stock = -1.

Fix: Use an atomic updateMany with a where: { stock: { gte: item.qty } } guard and check result.count.

Discount limit race (discount-service.ts + order-service.ts): isDiscountApplicable reads usage counts, but the actual DiscountUsage record is created later in a separate transaction in order-service.ts. Two concurrent requests both read totalUsage = 0 (maxUses = 1), both pass, and both create usage records. The DiscountUsage table has no unique constraint on (discountId, userId) — duplicates are silently permitted.

Fix: Move the usage check + increment into the same transaction, or add a unique constraint and handle the violation.

Critical
C2 · src/bots/client/client-bot-interactive.ts:618-631,808-811 and many more in manager-bot-interactive.ts
Callback answer dedup guard silently eats all user-facing feedback

The pattern starts every callback handler with await answerCallback() (setting callbackAnswered = true), then later calls like answerCallback({ text: "محصول یافت نشد", show_alert: true }) are all silently skipped because the guard (if (callbackAnswered) return) triggers.

Impact: Users see zero toast notifications. "Added to cart", "Product not found", "Error processing order" — none of these alerts ever appear. This affects every callback in both client and manager bots (~40+ call sites).

Fix: Remove the initial answerCallback() call. Only call answerCallback when you actually have feedback text to show. Or restructure to call the default only if no explicit answer was given.

Critical
C3 · src/bots/client/client-bot-interactive.ts:286
Markdown parse error crashes bot on /start when user name contains special characters

ctx.reply(welcomeText, { parse_mode: "Markdown" }) without error handling. If the welcome text contains Telegram-special Markdown characters (_, *, [, etc.) — which come from user input like user.firstName — Telegram's API throws Can't parse entities.

At risk: Every user whose name, phone number, or free-text input includes Markdown metacharacters will crash the /start handler. This affects all 3 bots, not just the client.

Fix: Always pass user-provided strings through escapeMarkdown() before sending with parse_mode: "Markdown". Or use safeRender which already has the fallback pattern.

Critical
C4 · src/utils/safe-reply.ts:116-124
safeRender retry path has no error handling — can crash the bot

safeRender catches the first editMessageText call, but the fallback (delete + reply on line 122) has zero try/catch. If the fallback also fails (bot blocked, chat not found, message to delete not found), the error propagates unhandled — crashing the current handler.

Fix: Wrap the fallback block in a try/catch with isIgnorableError check, and log any non-ignorable errors.

Critical
C5 · src/jobs/send-invites.worker.ts:70-127
Duplicate channel messages on retry after partial failure — spams checkout channel

The channel message is sent (line 71-82), and if the invite link creation after it fails (line 92-96), the order.update is never called, so channelMessageId is lost (only in a local variable). On the next tick, a new channel message is sent — creating duplicate messages in the checkout channel.

Fix: Either (a) create the invite link first, then send the channel message, or (b) persist channelMessageId early in a separate DB update.

Critical
C6 · src/jobs/send-invites.worker.ts:100-124 + src/jobs/expire-invites.worker.ts:63-88
DB state mutated before user notification — if notify fails, user is left in the dark

Both workers update the order status before notifying the user:

send-invites.worker.ts: Order status set to INVITE_SENT (line 103) before notifying (line 120-124). If notification fails, the order is stuck at INVITE_SENT with a valid invite link but the user never receives it.

expire-invites.worker.ts: Order cancelled (line 63-78) before notifying (line 81-88). If notification fails, the user's order is cancelled without their knowledge.

Fix: Swap the order: notify first, then update DB. Or use an outbox pattern where the notification is a fire-and-forget side effect after successful DB write.

If order.inviteLink is already set, the method returns it immediately (line 52-54) without checking: (a) whether the Telegram link has been revoked (e.g., by cleanupChannelForOrder), or (b) whether the order status is still valid — the status check on line 56 is skipped entirely.

B3 · src/bots/client/client-bot-interactive.ts:398-425
Referral code created even after canCreateReferral permission revoked mid-flow

The callback handler checks canCreateReferral before setting session state referral_score. But the text handler (line 398) where the user submits the score does not re-check the permission. If the manager revokes the permission between entering the state and submitting, the referral code is still created.

Bug
B4 · src/bots/manager/manager-bot-interactive.ts:1277
escapeMarkdown(null) throws — product description shown as "null" crash

escapeMarkdown(product.description) || '—' — if product.description is null, escapeMarkdown(null) is called, which likely throws (the function calls .replace on its argument). Should be product.description ? escapeMarkdown(product.description) : '—'.

Bug
B5 · src/bots/client/client-bot-handlers.ts:113
Fractional quantity accepted via text command — corrupts cart data

qty is parsed as Number() but never validated to be an integer. User passes /add 1 1.5 and gets a fractional cart item quantity. Prisma's Int field truncates silently or throws depending on the driver.

Bug
B6 · src/bots/client/client-bot-handlers.ts:146-152
Price snapshot overwritten on re-add — undermines price protection guarantee

When re-adding an existing cart item, unitPriceSnapshot is overwritten to the current product price AND quantity is incremented. If the price changed between additions, the old units are re-priced too. The README advertises "protects against price changes" but does the opposite for repeat additions — customers could be charged mixed prices for the same product.

Bug
B7 · src/bots/client/client-bot-handlers.ts:113-290
Blocked users bypass isActive check — can still interact via legacy handlers

ensureUser never checks user.isActive. ClientTexts.userBlocked() exists in texts.ts:39 but is never called. Blocked users can still browse products, add to cart, and checkout via the command-based handlers. The interactive bot does check this correctly — but the legacy handlers don't. (Low impact if legacy handlers are truly unused, but they're still in the codebase and compiled.)

Bug
B8 · src/infra/scheduler/interval-scheduler.ts:29-75
setInterval causes overlapping job runs — concurrent DB operations corrupt state

If a job takes longer than its interval (e.g., the 2-minute expire-invites job hits Telegram rate limits and takes 3 minutes), a new instance starts executing concurrently on shared data. Both workers process the same orders, both clean up the same channels, both send duplicate notifications.

Fix: Use a running-flag guard or switch to recursive setTimeout pattern (setTimeout(job, interval) at the end of each run).

Bug
B9 · src/jobs/expire-invites.worker.ts:52-60
Unhandled error in loop halts all subsequent order processing

If cleanupChannelForOrder throws (non-ignorable Telegram error, DB timeout), the entire for loop halts. All subsequent expired orders are skipped until the next cron run. Each order's processing should be wrapped in its own try-catch.

Same pattern exists in notification-service.ts where one failing manager blocks all remaining notifications (no Promise.allSettled).

Bug
B10 · src/services/channel-cleanup-service.ts:66-72
Channel fields cleared even if Telegram cleanup fails — retry becomes no-op

The order.update setting channelMessageId: null and inviteLink: null runs unconditionally after three Telegram operations. If those operations fail with non-ignorable errors (caught and logged), the order fields are still cleared. On the next retry, the cleanup logic sees null fields and skips all cleanup — leaving the user potentially still in the channel and the invite active.

Bug
B11 · src/services/order-service.ts:53-54
Wrong error class on cart ownership mismatch — misleads callers

if (!cart || cart.userId !== userId) { throw new CartNotFoundError() } — when cart exists but doesn't belong to this user, the error says "cart not found". This is misleading for logging, debugging, and any calling code that catches this error. Needs a dedicated CartNotOwnedByUserError.

Bug
B12 · src/services/order-service.ts:73-74
Inactive/missing product throws semantically wrong error

Throws InsufficientStockError("Product is not available") when the product is inactive or doesn't exist. This is not a stock issue — it's a product availability issue. Needs a separate error class like ProductNotAvailableError.

Bug
B13 · src/services/bot-settings-service.ts:19-42
Catch-all error swallowing masks DB connection failures

Both get() and delete() wrap their database operations in try { ... } catch { return null; }. This catches everything — including DB connection failures, permission errors, and constraint violations — and silently returns null. A database outage would cause all settings to silently fall back to defaults instead of throwing an error that could be surfaced.

Fix: Only catch specific Prisma errors (P2021 for missing table, P2025 for missing record).

Bug
B14 · src/utils/session-store.ts:14
Session key type is number — breaks for large Telegram user IDs

SessionStore<T> uses number as its key type, but Telegram user IDs can exceed Number.MAX_SAFE_INTEGER (9,007,199,254,740,991). In courier-bot-interactive.ts:200,349, Number(courier.tgUserId) is used as a session key — this silently loses precision for large IDs. Should use string keys or bigint.

🔗 Cross-Cutting Concerns 4 systemic themes

1. Side Effects Before DB Writes — notification order is wrong everywhere

Pattern: In send-invites.worker, expire-invites.worker, and various handler paths: DB is mutated first, then the user is notified. If the notification fails, the DB state is already committed.

Fix: Notify first (best-effort), then write to DB. Or write to DB + add a "notification pending" flag and have a worker retry. The current pattern leaves users in inconsistent states.

2. No Concurrency Safety — race conditions are systemic

Affects: Stock decrement, discount usage recording, cart creation, order status transitions, scheduler job overlapping, setInterval without overlap guards.

Since the project uses SQLite which doesn't support concurrent write connections, the practical concurrency is limited — but async/await within a single process still interleaves operations. The scheduler overlap bug (B8) is the most likely to manifest.

3. The Interactive Bots Are Untested — 4,174 lines of critical UI logic have zero coverage

Files: client-bot-interactive.ts (1,479), manager-bot-interactive.ts (2,310), courier-bot-interactive.ts (385).

All the bugs found (C2, C3, B3, P1, P2, P16, N1, N2, N4, I16, S4, S6) are in these files. The legacy command handlers have tests but aren't used in production. The actual production code paths have zero automated tests.

4. Test Infrastructure Fragility — shared SQLite DB, no isolation, skipped tests

Problems:

  • All tests share the same dev.db file — parallel execution causes cross-test pollution
  • manager-bot-handlers.test.ts has a .skipped test because of this (P14)
  • No separate test database or transaction rollback strategy
  • Coverage thresholds are set to 90% but likely unmet for interactive code
  • Consider using :memory: SQLite for tests and wrapping each test file in a transaction
