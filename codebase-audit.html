R1 Cart operations not wrapped in transactions — duplicate carts, lost quantities
client-bot-interactive.ts:784-816, 849-882 · client-bot-handlers.ts:129-162
Three separate locations implement an add-to-cart flow using 3–4 sequential Prisma queries (find cart, create-if-missing, find item, upsert) with no transaction boundary. Two concurrent requests for the same user can create duplicate carts, duplicate cart items, or lose a qty increment.
let cart = await prisma.cart.findFirst({ where: { userId: user.id, state: CartState.ACTIVE } }); // RACE: both see no cart if (!cart) { cart = await prisma.cart.create({ ... }); // Two active carts created } const existingItem = await prisma.cartItem.findFirst({ ... }); // RACE: both see no item if (existingItem) { await prisma.cartItem.update({ ... data: { qty: existingItem.qty + qty } }); } else { await prisma.cartItem.create({ ... }); // Two items created for same product }
race condition

client-bot-interactive.ts:100-138
The usedCount >= effectiveMaxUses check at line 115 and the increment: 1 update at line 131 are separated by async boundaries. Two concurrent users can both pass the check and both successfully redeem a single-use code, since the isActive: false write happens after both checks have passed.

R3 Double order approval / approve-vs-reject race — duplicate invites, double messages
manager-bot-interactive.ts:694-939 (approve) · 943-995 (reject)
Two managers clicking "approve" on the same order simultaneously: both see AWAITING_MANAGER_APPROVAL, then proceed through ~30 sequential await operations (DB reads, Telegram API calls, file downloads, invite link creation, notifications) before the final order.update. Result: two payment messages posted, two invite links created, two client notifications sent. The same race exists between approve and reject — an order can end up both approved and rejected.

R4 Session state read-modify-write race — lost qty increments, corrupted state transitions
client-bot-interactive.ts:750-769 · manager-bot-interactive.ts:126-128 · (14+ occurrences)
The SessionStore.get() → modify → .set() pattern spans no atomic boundary. Two rapid callback queries from the same user (e.g., rapid inc/dec clicks) can both read the same selectedQty value, compute independently, and write back — one increment is silently lost. Same pattern in the manager text handler where session data accumulates across async steps.
const session = userSessions.get(ctx.from.id) || { state: "viewing_product", selectedQty: 1 }; let qty = session.selectedQty || 1; // RACE: both read 3 if (action === "inc") qty = Math.min(qty + 1, 99); // both compute 4 userSessions.set(ctx.from.id, { ...session, selectedQty: qty }); // both write 4 — intended: 5

R6 TOCTOU in discount usage validation — discounts can exceed maxUses
discount-service.ts:172-205 · order-service.ts:166-188

R7 Concurrent webhook processing — no update serialization per user
webhooks.ts:12-34
Telegram sends updates via HTTP POST to Fastify. Each POST runs in its own async handler with no queuing or serialization. Two callback queries from the same user (e.g., rapid inc + dec) arrive concurrently, amplifying all session race conditions above. Grammy's polling mode serializes per bot, but webhook mode does not.
concurrency
R8 Background scheduler runs concurrently with bot handlers — races on same DB rows
interval-scheduler.ts · expire-invites.worker.ts · send-invites.worker.ts
The interval scheduler runs processExpiredInvites (every 2 min), processSendInvitesBatch (every 60s), and expireIdleCarts (every hour) concurrently with bot handlers. A manager could approve an order while the expire worker cancels it. The approve flow could process an order whose cart was just expired by the cleanup worker.

order-service.ts:89-117
